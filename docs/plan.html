Build plan / draft 2

sessionscribe

Claude Code already writes a full transcript of every session. This reads it and keeps four markdown docs per repo current — automatically, with no manual input — using a second agent so your own session stays out of it.

Trigger every Claude reply Writer opencode, configurable model Scope per repo Phases 8
01

The loop

Claude finishes a reply │ ▼ Stop hook ────────── no model, exits in ms │ gets session id, transcript path, cwd ▼ queue + per-repo lock │ │ busy? ──▶ mark pending, exit ▼ opencode run │ ├── reads transcript bytes since last run ├── reads the four docs as they stand └── edits whichever docs actually changed │ ▼ pending set? ──▶ run again, covering what arrived

The docs are the memory. That's how a run knows what an earlier run claimed, and can take it back — which is the normal case, not an edge case.

02

Locked

01
Trigger on every Claude reply, not on session end
Session end can't be caught reliably — crash, kill, closed window, all silent. A reply ending always fires.
02
Writes go straight to the real docs, corrections included
If reply 2 claims a thing and reply 3 scraps it, the next run pulls it from PROJECT and writes a DECISIONS entry saying why it was dropped. Being wrong and reversing is recorded, not hidden.
03
One run at a time per repo, with coalescing
Queue plus a lock. Triggers landing during a run set a pending flag and the current run picks them up on finish. Two processes never edit the same file, and no reply goes uncovered.
04
Each run reads only new transcript bytes plus the current docs
Flat cost no matter how long the session runs. A 4 MB transcript never gets re-read, and small models stay viable.
05
CLAUDE.md is a skill you run, not part of the pipeline
That file steers every future session. It gets your main model, on demand, where you can see it — never a cheap model writing unattended.
06
The writing model is config
Any provider opencode supports. Free models, fable, sol, whatever — one string in a config file.
07
It can read the code, but the transcript leads
Read-only access to the repo, used to check claims rather than to source them. Stops the common failure where something was discussed at length, never built, and lands in the changelog anyway. Weighting is configurable, code access can be turned off.
08
One command onboards a repo
scribe init seeds PROJECT and DECISIONS from the repo itself, then replays that repo's past sessions into CHANGELOG and JOURNAL. Run once, per repo, when someone turns it on. Backfill isn't a separate thing — it's the second half of this.
09
Docs live in docs/scribe/
Fixed folder named after the tool. Nothing to detect, no collision with docs you already keep, obvious at a glance which files are machine-written.
10
Git is the undo, and committing stays yours
No snapshot system, no auto-commit, no interference with your history. A bad write is a git checkout away — provided there's a commit to go back to. See the risks.
03

The four docs

docs/scribe/ PROJECT.md what it is, where it stands DECISIONS.md what was chosen, and what was dropped CHANGELOG.md dated, what happened JOURNAL.md the mess, in full INDEX.md one line per session digests/ weekly, grouped
Business context — current state only, no history
PROJECT.md
What this thing is, who it's for, where it stands. Rewritten in place as reality moves.
DECISIONS.md
One block per decision, each marked active, dropped, or superseded. Dropping carries the reason.
Engineering history — kept forever
CHANGELOG.md
Dated lines. What was built, what was fixed, what was ripped out.
JOURNAL.md
The mess. What you were stuck on, what the AI got confidently wrong, what you tried that failed, what the fix turned out to be. This is the one that stops mistakes repeating.

Most engineering sessions never touch PROJECT or DECISIONS. Those two only move when the session actually contains product-level talk — otherwise they're left alone.

04

Interface

Mostly there isn't one. The normal state is invisible — you work, the docs update. The CLI exists for setup, and for the moments you don't trust it.

The writer: hardcoded connectors

One connector per supported agent, each owning that tool's flags, output and failure modes. Not a generic command template — a template pushes every tool's quirks onto the user, and the first thing they hit is a silent hang because they forgot the auto-approve flag. opencode ships first; claude, codex and gemini are small additions. A custom escape hatch exists and is explicitly your problem if it breaks.

[writer] agent = "opencode" model = "opencode/deepseek-v4-flash-free" [code] read = true # let it look at the repo weight = "check" # verify claims only, don't source from code
On and off

Off everywhere by default. scribe init turns it on for one repo and it stays on. Nothing ever runs where you didn't ask.

The catch: you have to remember, and the sessions most worth keeping are the early ones in a new project — exactly when scribe isn't on your mind. Mitigation that doesn't break the zero-input rule: after several sessions in an uninitialised repo, one line, once — "scribe isn't on here — 6 sessions so far." A nudge, not a prompt. Turning it on late still recovers the history, because init replays.

Commands
scribe init
Turn it on here: install the hook, seed the docs, replay history. The only command most people ever run.
scribe status
On or off, last run, anything queued, anything failing.
scribe diff
What the last run changed.
scribe run
Go now, don't wait for a reply.
scribe off / on
Pause without uninstalling — sensitive work, or a thrashy session you don't want on the record. Expires at end of day unless you pass --stay, because a pause you forget fails the same way forgetting to turn it on does.
scribe doctor
Is the hook installed, does the writer command actually work, is the model reachable.
/claude-md
The skill. Reads the four docs, writes a short CLAUDE.md with your main model, shows the diff first.
Stack

Go, cobra for the command tree, huh for the init wizard. The hook fires on every reply, so startup cost is the one hard constraint — a static Go binary starts in single-digit milliseconds with nothing to install alongside it.

huh earns its place in exactly one command. scribe init is the entire onboarding and should feel considered: pick your agent, pick your model, confirm the path, watch the replay, see what it wrote before it touches the repo. Everything else is plain stdout — status, diff and doctor are output, not interaction.

Not OpenTUI, for now. It's good, and it's what opencode itself runs on — but it's a full-screen rendering engine, and scribe is seven commands and one form. Adopting it means taking Bun and TypeScript onto the hook path to get a wizard huh does in forty lines. Where it would earn its place: scribe browse, a reader for journals and digests — scroll entries, jump by date, search for the bug you know you hit before. That's a real TUI and deserves a real TUI library. Not in these phases; the docs have to be worth reading first.

Phases

00
half day
Prove it before building it
Three unknowns, all cheap to settle, all fatal if wrong.
  • Confirm the Stop hook actually fires here and hands over session id, transcript path and cwd
  • Confirm opencode run --auto completes unattended with no terminal attached
  • Feed this session's own transcript to two or three candidate models and compare against what really happened — we both know the right answer for this one, which makes it a real test
GateIf no model writes prose you'd actually keep, stop here. Everything downstream is plumbing around that one capability.
01
1–2 days
The loop, one repo, one person
End to end and genuinely working, with nothing configurable yet.
  • scribe hook — reads the hook payload on stdin, enqueues, exits. Budget under 50 ms, no network, never blocks your session
  • Queue, per-repo lock, pending flag, coalescing
  • scribe run — the worker: new bytes in, four docs read, opencode called, docs edited
  • Byte offset per session so re-runs don't duplicate and resumed sessions pick up where they left off
  • Single Go binary. The hook path has to be instant and dependency-free
Done whenYou work for an hour, touch nothing, and the four docs are current and correct afterwards.
02
1–2 days
scribe init — turning it on for a repo
The onboarding story, and the thing that makes the docs useful on day one instead of week three. Built before prompt tuning because it produces the corpus that tuning needs.
  • Seed pass: read the README, package files, directory tree and any existing docs to write a first PROJECT.md and DECISIONS.md
  • Replay pass: work through that repo's existing transcripts into CHANGELOG and JOURNAL
  • Chunked and resumable — some session histories are large
  • Dry run by default, writing somewhere you can read before it touches the repo
  • Uses the good model. It runs once per repo, so it's the wrong place to economise
Falls out of thisA real corpus of varied output to tune against in phase 03, instead of waiting around for live sessions to happen.
03
2–3 days
Make the writing good
The longest phase, and the one that decides whether you keep using this.
  • A separate prompt per doc — four small jobs beat one big one
  • PROJECT and DECISIONS gated behind "did anything product-level actually happen"
  • The correction path: pulling an entry always writes the reason into DECISIONS
  • Teach the journal what's worth capturing — problems hit, AI mistakes, dead ends, the actual fix
  • Tune how hard it checks the code before believing the transcript
  • Size caps on the edited docs, so the model can hold one whole and edit it safely
  • Iterate against the phase 02 corpus until output stops embarrassing you
04
1 day
Config and safety
Before it runs on anything that matters.
  • Off by default, opt in per repo — no surprise files appearing anywhere you didn't ask
  • Config: model, code-reading weight, ignore rules
  • Redaction pass before anything leaves the machine. Transcripts contain whatever was on screen, keys included
  • scribe status and scribe diff — a silent background writer you can't inspect is a background writer you won't trust
05
1 day
Digest and index
Makes the history navigable instead of just long.
  • Weekly digest, grouped features / bugs / general work, sessions listed under each
  • Session index — one line each, dated, skimmable
  • No scheduler: the first run of a new week notices and writes last week's digest. Nothing to install, nothing to keep alive
06
1–2 days
Teammates
Blocked on a layout decision — see open questions below.
  • Pick the file layout, then build to it
  • Attribution on entries
  • Behaviour when two people's docs land in the same commit
07
half day
The CLAUDE.md skill
Reads the four docs, writes something small and sharp. Your model, on demand.
  • Slash command in Claude Code
  • Hard length ceiling — the value is in it being short
  • Shows the diff before it writes
06

Open

How teammates write to the same journal

Committed docs mean everyone's scribe appends to the same files — a merge conflict in machine-written markdown on nearly every pull. Blocks phase 06.

A
One file per session. journal/2026-08-08-auth-refactor.md plus a generated index. Two people can't touch the same file, so conflicts are impossible by construction. Also fixes the long-file readability problem. Costs you a directory of many small files.
B
One file per person. journal/sahil.md. No conflicts, fewer files, but each one grows without limit and reading across people means opening several.
C
Shared files, live with conflicts. Simplest layout, and the one you'll resent. Auto-generated conflict markers are the worst kind to resolve.
What it's called — scribe is a working name and it's already baked into the docs folder path, so worth settling before phase 02.
Default writing model — settle after phase 00 tells us which ones can actually do the job.
Journal splitting — one file forever, or per month. Answered for free if the team question lands on A.
Committed or ignored — gitignore for the first week regardless, until the output earns its way in. Note this sits awkwardly with git being the only undo.
Monorepos — one docs/scribe/ per repo assumes one product per repo. Fine for now; revisit if it bites.
07

What could sink it

!
The writing model isn't good enough
Pulling what mattered out of a long messy conversation is the hard version of this task, not the easy one. There's no clever architecture that saves you here. Phase 00 exists to find this out in half a day instead of a week.
!
The transcript format is undocumented
It's an internal file that can change between CLI versions. Two traps confirmed already: tool results are recorded as user messages, and subagent turns are mixed in and have to be filtered. Pin the parser to known shapes and fail loudly rather than writing nonsense quietly.
!
The undo has a hole in it, by choice
Git is the recovery path, but nothing commits the docs — so the floor only exists as far back as you last committed. An afternoon of bad runs on an uncommitted PROJECT.md has nothing to restore from, and neither do repos that aren't git repos. Accepted deliberately to keep the tool out of your history. Worth revisiting if it actually bites; committing the docs yourself at the end of a session closes most of it.
!
Nobody reads it
The stated goal is that mistakes don't repeat. That only pays off if the journal stays readable — which is what the index and the digest are for, and why the edited docs are size-capped.
!
It ships your session contents somewhere
Transcripts hold whatever was on screen. A hosted free model means all of that goes to whoever runs it. Redaction plus per-repo opt-in in phase 03, before this points at anything real.
